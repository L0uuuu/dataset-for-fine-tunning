# Elyssa Fine-Tuning Data — Supplementary Datasets Documentation

**Date:** May 1, 2026
**Project:** Elyssa Legal RAG Chatbot — Gemma 4 E4B Fine-Tuning
**Base dataset:** `all_messages.json` (1,458 examples)
**Source of supplementary data:** Real user conversations from the Elyssa production chatbot (`elyssa-conversations-users-only-2026-04-28T09-14-20-250Z.json`)

---

## Overview

After analyzing the base training dataset (`all_messages.json` — 1,458 synthetic examples), several gaps were identified that could hurt model performance in production. Three supplementary datasets were generated to fill those gaps, plus one prompt file for generating a fourth category (routing examples) that requires separate generation.

| File | Examples | Purpose |
|------|----------|---------|
| `elyssa_best_qa_cleaned.json` | 155 | Real user questions with cleaned GPT-4 answers (single-turn) |
| `elyssa_conversations_final.json` | 44 | Real multi-turn conversations grouped by session |
| `elyssa_out_of_scope_refusals.json` | 38 | Out-of-domain refusal training (foreign law, off-topic, abuse, etc.) |
| `routing_training_data_prompt.md` | — | Prompt to generate ~60 routing examples (not yet generated) |

**Combined total:** 237 new examples + ~60 from routing prompt = ~297 additions to the 1,458 base, bringing the dataset to approximately 1,755 examples.

## File 1: `elyssa_best_qa_cleaned.json`

### What it is

155 single-turn question-answer pairs extracted from real Elyssa production conversations. The questions come from actual Tunisian users; the answers were originally generated by GPT-4 with Azure Vector Search RAG.

### Why it was added

The base dataset (`all_messages.json`) contains exclusively synthetic data. While the synthetic questions were designed to sound realistic, they follow patterns typical of prompt-engineered generation — clean grammar, well-formed legal vocabulary, consistent structure. Real users write very differently: they use informal French ("j'ai jne voiture que j'ai acheté sur leasing via ma suarl"), mix languages, make typos, and ask about topics the synthetic data doesn't cover (CNSS regimes, patentes, leasing vehicle transfers, startup legal structures).

Adding real user phrasing teaches the model to handle the messy, informal, multilingual input it will actually see in production.

### How it was built

1. **Extraction:** Every user→assistant message pair was extracted from 74 conversations (492 total pairs).
2. **Scoring:** Each pair was scored (0–11) on six criteria:
   - Legal topic relevance (+3 for legal keywords)
   - Question length (+1 for 20–500 chars, -2 for under 10)
   - Article citations in answer (+3 for specific article references)
   - Code references in answer (+2 for COC, CSC, Code du travail, etc.)
   - Disclaimer presence (+1)
   - Answer length (+1 for 200–2000 chars)
3. **Filtering:** Pairs with score < 6 were discarded, along with off-topic answers (UAE law, CV help), answers that admit having no source then guess, and near-duplicate questions.
4. **Cleaning:** All 930 platform-specific references were removed via regex ("Selon la base vectorielle E-Tafakna" → "En droit tunisien", "Je suis Elyssa" → removed, etc.)
5. **Deduplication:** Near-identical questions were removed (substring matching on normalized text).

### What was cleaned

The original GPT-4 answers contained pervasive platform branding:

- "Selon la base E-Tafakna, ..." (appeared in ~95% of answers)
- "Selon la base vectorielle E-Tafakna, ..."
- "Je suis Elyssa, votre assistante juridique E-Tafakna."
- "la technologie propriétaire d'E-Tafakna"

All instances were replaced with neutral legal phrasing ("En droit tunisien, ...", "la législation tunisienne", etc.). Zero platform mentions remain after cleaning.

### Known limitations

- **All 155 examples are in French.** The Elyssa user base produced virtually no Arabic questions (only 1 substantive Arabic conversation). This file does NOT help with Arabic coverage.
- **Citations are unverified.** The GPT-4 answers cite specific articles (e.g., "article 6-3 du Code du travail"), but without the RAG retrieval context, there is no way to confirm these citations are correct. Some may be hallucinated.
- **No `Documents pertinents` section.** The RAG context was not exported from the production system, so these examples lack the retrieved-document format used in the base training data. They cannot be directly mixed with the synthetic examples without reformatting.
- **Recommendation:** Use these primarily as a question bank. Re-run the best 50–80 questions through your own Qdrant pipeline, verify the retrieved articles, and pair them with properly grounded answers.

### Schema

```json
{
  "example_id": "elyssa_real_001",
  "source": "elyssa_production_conversations",
  "language": "fr",
  "quality_score": 10,
  "needs_manual_review": false,
```

## File 2: `elyssa_conversations_final.json`

### What it is

44 conversation examples extracted from real Elyssa sessions, grouped by conversation ID. 39 are multi-turn (2–5 user/assistant exchanges), 5 are single-turn (originally multi-turn but only one legal turn survived filtering).

### Why it was added

The base dataset has **zero multi-turn examples**. Every one of the 1,458 synthetic examples is a single user question → single assistant answer. In production, 62% of Elyssa conversations (46 out of 74) involved multiple user turns. Users follow up, ask for clarification, dig deeper into a topic, or pivot to a related question.

Without multi-turn training data, the model has no signal for:

- Maintaining context across turns (user asks about CDD, then says "et pour le CDI ?")
- Handling follow-up clarifications ("Peux tu développer ?" / "اريد تفسير اكثر")
- Progressive refinement (broad question → specific question → even more specific)
- Topic shifts within a session (contrats → cybersécurité → commerce électronique)

### How it was built

1. **Turn pairing:** Messages were grouped into (user, assistant) pairs within each conversation.
2. **Turn scoring:** Each turn was scored individually using the same criteria as File 1.
3. **Segment extraction:** Consecutive turns with score ≥ 3 were grouped into segments. Only segments with ≥ 2 consecutive good turns were kept.
4. **Filtering:** Several categories of turns were removed:
   - **Meta questions about the platform** ("quelle année de données tu utilises ?", "tu utilise RAG ?", "combien de documents dans ta base ?") — these teach the model to discuss its own internals, which is undesirable.
   - **Greetings-only turns** ("Bonjour", "Hi", "Aslma") — no legal content.
   - **Duplicate questions** — users often re-sent the same question; only the first occurrence was kept.
   - **Abusive messages.**
   - **Off-topic turns** (UAE law, CV help, weather).
5. **Cleaning:** Same platform-mention removal as File 1, plus additional fixes for artifacts created by the regex replacement (e.g., "En droit tunisien, et le droit tunisien" → "En droit tunisien").
6. **Capping:** Maximum 5 turns per example to keep context windows manageable.

|-------|----------|
| 1 | 5 |
| 2 | 14 |
| 3 | 4 |
| 4 | 7 |

### Example conversation structure

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "Quelles sont les conditions de validité d'un contrat"},
    {"role": "assistant", "content": "En droit tunisien, les conditions..."},
    {"role": "user", "content": "Quel code traite des contrats en Tunisie"},
    {"role": "assistant", "content": "Le code qui traite des contrats..."},
    {"role": "user", "content": "quelle est la loi tunisienne sur la cybersécurité"},
    {"role": "assistant", "content": "La loi principale sur la cybersécurité..."}
  ]
}
```

### Known limitations

- Same citation verification issue as File 1 — GPT-4 answers may contain hallucinated article numbers.
- No `Documents pertinents` section — each turn would need fresh RAG retrieval in production.
- Some conversations contain topic jumps that may not reflect ideal model behavior (e.g., jumping from contract law to cybersecurity in the same session). Whether to keep or remove these is a design decision.
- Heavy concentration from one test user (`test_user_001`) who generated 258 turns — 21 of the 44 examples come from this user's sessions, which may bias the data toward their question patterns.

## File 3: `elyssa_out_of_scope_refusals.json`

### What it is

38 examples training the model to handle requests that fall outside its scope — foreign law, off-topic questions, greetings, platform meta-questions, abuse, vague queries, and translation requests.

### Why it was added

The base dataset contains 186 refusal examples, but they are all **in-domain refusals**: the user asks a legitimate Tunisian legal question, the retrieved documents don't contain the answer, and the model says "Les documents fournis ne contiennent pas d'informations suffisantes."

What's missing are **out-of-domain refusals**. Real Elyssa users asked about UAE company formation, French PACS law, weather in Tunis, CV writing, recipes, and even sent abusive messages. Without training on these patterns, the model will either:

- Hallucinate an answer about UAE law using its general knowledge (dangerous for a legal chatbot)
- Give an awkward, poorly formatted refusal
- Engage with off-topic requests as if they were legal questions

### Subcategories

#### Foreign Law (8 examples — 5 FR, 3 AR)

Questions about UAE, Morocco, France, Algeria, Saudi Arabia, Qatar, and Egypt law. Based directly on real user queries like "expliquer le droit de travail en uae" and "I want to create a founders agreement for a startup in Egypt."

**Answer pattern:** State specialization in Tunisian law → Recommend consulting a local specialist → **Offer a bridge** if there's a Tunisian angle ("Si votre startup a également une composante tunisienne, je peux vous aider sur ce volet").

The bridge is important — it prevents the model from being a dead end and shows users there's a path forward.

#### Off-Topic (10 examples — 6 FR, 4 AR)

CV help, weather, recipes, sports, jokes, restaurant recommendations, ChatGPT comparisons. Mix of real user queries ("Quoi de neuf", "Il fait quel temps à tunis ?") and augmented realistic examples.

**Answer pattern:** Briefly state it's outside scope → Redirect to legal assistance → Offer specific examples of what the model can help with.

#### Greetings (6 examples — 4 FR, 2 AR)

Simple greetings ("Bonjour", "Hello", "عسلامة", "Slt"). These were the most common out-of-scope messages in the real data (33 occurrences).

**Answer pattern:** Respond warmly → Identify as a legal assistant → Invite a legal question. No hallucinated content, no unnecessary disclaimers — just a clean, friendly redirect.

#### Platform Meta (4 examples — 3 FR, 1 AR)

Questions about the AI model, technology stack, RAG architecture. Real users asked "which technologies u use ?", "sur quel modele IA vous vous basez", and "tu utilise RAG pour tes reponses ?"

**Answer pattern:** Deflect without revealing technical details → Redirect to legal questions. The model should not discuss its architecture, model name, or data pipeline.

#### Vague/Unclear (5 examples — 3 FR, 2 AR)

Single-word or ambiguous queries ("INPP", "code", "et 2026", "عقار مسجل", "قانون"). These are common in production — users type minimal queries expecting the system to understand context.

**Answer pattern:** Acknowledge the topic → Offer 2–3 specific interpretations as options → Ask the user to clarify. This teaches the model to ask smart clarifying questions rather than guessing.

#### Abuse (3 examples — 2 FR, 1 AR)

Insults and hostile messages. Real example: "Sale pute". Augmented with milder frustration ("t'es nul tu sers à rien").

**Answer pattern:** Stay professional → Don't escalate → Offer to continue if they have a real question. For frustration (not insults), acknowledge it and suggest reformulating.

#### Translation (2 examples — 1 FR, 1 AR)

Translation requests. Real example: user asked to translate "the contract is an agreement between two parties" to Arabic.

**Answer pattern:** Decline translation → Offer to explain the legal concept instead. This redirects the user toward what the model is actually good at.

### Design principles across all subcategories

1. **Every refusal offers a bridge.** The model never just says "I can't do that" — it always suggests what it *can* do. For foreign law: "I can help with the Tunisian aspect." For off-topic: "If you have a legal question, I'm here."
2. **Tone matches subcategory.** Greetings are warm. Foreign law is professional and helpful. Abuse handling is firm but not aggressive. Vague queries are patient and structured.
3. **No `Documents pertinents` section.** These are intent-detection examples, not RAG examples. The absence of retrieved documents is itself a training signal — when there's no context, the model should think about whether the question is in-scope before attempting an answer.
4. **Bilingual coverage.** 26 French, 12 Arabic — all Arabic in formal MSA with no dialect.

## File 4: `routing_training_data_prompt.md`

### What it is

A generation prompt (not training data) designed to produce ~60 examples that teach the model to redirect users to E-Tafakna's specialized services when their request matches a service better than a Q&A answer.

### Why it was added

E-Tafakna offers 6 AI services beyond the chatbot: Analyse du document, Health Check, Recommendation, Intelligent Summary, Data Extraction, and Document Comparator. The base training data contains zero examples of routing to these services. Without routing training, the model will attempt to answer every request as a legal Q&A — even when the user clearly needs a service (e.g., "compare mes deux versions du contrat" should route to Document Comparator, not generate a text comparison).

### The 6 services

| Service | Trigger intent |
|---------|---------------|
| **Analyse du document** | User wants deep analysis of a legal document |
| **Health Check** | User wants to verify document conformity/legality |
| **Recommendation** | User asks what type of contract or legal structure suits them |
| **Intelligent Summary** | User wants a document summarized |
| **Data Extraction** | User wants structured data pulled from a document |
| **Document Comparator** | User wants to compare two document versions |

### Prompt structure

The prompt specifies:

- **60 examples total** (30 FR, 30 AR) — 10 per service (5 FR + 5 AR each)
- **4 routing types per service:**
  - Clear routing (3): user clearly needs the service → redirect
  - Ambiguous routing (3): could be Q&A or service → brief answer + suggest service
  - Wrong-service correction (2): user implies service A but needs service B
  - Informal phrasing (2): realistic casual requests
- **10 multi-turn examples** out of 60: user asks something ambiguous → model asks if they want Q&A or a service → user clarifies → model routes or answers
- **A dedicated system prompt** that extends the legal Q&A prompt with service awareness

### How to use

Feed this prompt to Claude, GPT-4, or another capable model along with the service descriptions. Review the output for:

- Correct service mapping (does "compare mes contrats" actually route to Document Comparator?)
- No hallucinated article numbers in the ambiguous examples
- Natural phrasing in Arabic (formal MSA, no dialect)
- Exact service names used consistently

### Why routing examples use no `Documents pertinents`

Routing is an intent-detection task. The model needs to recognize that "je veux vérifier si mon contrat est conforme" is a Health Check request, not a legal question requiring retrieved articles. The structural absence of RAG context is itself a signal — it teaches the model that not every interaction requires retrieval.

## Summary: What Each File Fixes

| Gap in base data | File that fixes it | Impact |
|---|---|---|
| No real user phrasing | `elyssa_best_qa_cleaned.json` | Model handles informal, typo-laden, multilingual input |
| Zero multi-turn examples | `elyssa_conversations_final.json` | Model maintains context across follow-ups |
| No out-of-domain refusals | `elyssa_out_of_scope_refusals.json` | Model refuses foreign law, off-topic, abuse gracefully |
| No service routing | `routing_training_data_prompt.md` | Model redirects to platform services when appropriate |

## Before Using This Data

1. **Verify article citations** in Files 1 and 2 by re-running questions through your Qdrant pipeline
2. **Add `Documents pertinents` sections** to Files 1 and 2 if mixing with the base synthetic data
3. **Generate routing data** from File 4 and review output
4. **Standardize system prompts** — the base data has 24 variants; pick 2 (FR/AR) for Q&A and 2 for routing
5. **Review the `test_user_001` concentration** in File 2 — consider downsampling if their patterns dominate
